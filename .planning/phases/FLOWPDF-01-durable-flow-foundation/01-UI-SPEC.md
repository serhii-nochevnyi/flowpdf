# Phase 1 — UI Design Contract

> Visual and interaction contract for the Phase 1 local **Foundation Inspector** walking skeleton. Generated by gsd-ui-researcher; awaiting gsd-ui-checker verification.

---

## Phase Boundary

The Foundation Inspector is a local browser verification harness, not the product editor. It proves that a user can create or open a sample FlowDocument, send one typed mutation through the command bus, undo or redo it, save, reload, recover, and inspect revision, provenance, and privacy-minimized audit records.

It MUST NOT introduce rich-text editing, caret/selection/IME behavior, document pagination or canvas rendering, PDF preview/export/import, field authoring, voice controls, collaboration, authentication, remote storage, or backend UI. The content shown is a compact semantic summary and diagnostic metadata, never an editable document surface. This enforces the Phase 1 boundary in `01-CONTEXT.md` and the Phase 1 research recommendation not to add React or Vite yet.

## Design System

| Property | Value |
|----------|-------|
| Tool | none — manual CSS custom properties and semantic HTML |
| Preset | not applicable; no `components.json` or existing frontend exists |
| Component library | none |
| Icon library | none; use visible Ukrainian text labels, not icon-only controls |
| Font | system UI stack: `system-ui, -apple-system, "Segoe UI", Roboto, "Noto Sans", Arial, sans-serif` |

The Phase 1 harness uses minimal TypeScript modules plus native HTML controls and CSS. This keeps the proof aligned with the Rust/WASM + IndexedDB adapter boundary and avoids installing a framework specifically for an inspector. React/Vite remain the preferred future editor shell from project stack policy, but are not justified by this phase alone. No shadcn initialization gate applies because no React/Next/Vite application is being created.

Visual direction: restrained professional document-tool aesthetic. Use a cool off-white application background, white data surfaces, thin neutral borders, modest corner radius (6px), and no gradients, illustrations, decorative shadows, or product marketing treatment. Let revision state and proof results carry hierarchy.

The primary screen focal point is the current document-session state and the result of the most recent operation in the main column. The create action leads only in the empty state; after creation, command controls and inspector metadata remain visually subordinate to the current revision, durability badge, canonical hash, and outcome status.

## Layout and Component Inventory

At widths of 960px and above, use a centered shell with `max-width: 1200px`, 24px page padding, and a two-column grid: a flexible primary work column plus a 360px inspector column. Below 960px, stack the inspector after the primary column; preserve source order and do not hide any operation. At widths below 480px, retain 16px side padding and let action groups wrap with 8px gaps.

| Area | Elements and behavior |
|------|-----------------------|
| App header | Product name `FlowPDF`, page title `Інспектор основи`, and a concise local-only label `Локальна перевірка`. Do not show account, sync, or collaboration affordances. |
| Document session card | Empty state until a document is created/opened. Once populated, show non-editable document ID, schema version, current revision, canonical hash, locale, and durable-state badge. IDs/hashes use copy buttons with accessible names and visual text labels. |
| Command panel | One primary `Створити тестовий документ` button when no session exists. With a document open, expose one named test action `Застосувати тестову зміну`; it sends a predefined, typed command with the displayed current revision as `baseRevision`. The UI never modifies the summary optimistically or directly. A secondary diagnostic action `Перевірити застарілу команду` deliberately submits an older revision and must return a non-mutating conflict. |
| History controls | Native buttons `Скасувати` and `Повторити`, disabled when their respective history direction is unavailable. Display the keyboard hints `⌘/Ctrl+Z` and `⌘/Ctrl+Shift+Z`; keyboard handling invokes exactly the same typed command path as the buttons. |
| Durability controls | `Зберегти локально` waits for IndexedDB transaction completion before announcing success. `Перезавантажити зі сховища` reopens the durable current revision. `Відновити останню стійку ревізію` runs recovery and renders either the verified durable revision or a structured recovery diagnostic. Do not label an uncommitted write as saved. |
| Inspector column | Three read-only sections: **Ревізія**, **Походження**, and **Аудит**. Revision shows the current revision/hash and command linkage. Provenance shows only create/migration lineage available in Phase 1, and explicitly states that PDF preview/export provenance is unavailable in this phase. Audit is a chronological table/list of redacted entries. |
| Status region | Persistent, text-first status beneath the relevant action group. Use `aria-live="polite"` for completion/progress and `role="alert"` only for failure/conflict/recovery diagnostics. Status always states outcome and next action; color never carries the meaning alone. |

Use semantic landmarks: one `<header>`, `<main>`, a labelled command `<section>`, an `<aside aria-label="Інспектор документа">`, and a labelled audit `<section>`. Use a real `<table>` for audit entries at desktop widths; at narrow widths it may become a definition-list/card representation with the same source order and labels.

## Interaction Contract

1. **Create/open:** On initial load, only `Створити тестовий документ` is primary. It creates a deterministic sample containing Ukrainian and English text plus existing required schema elements; it does not claim rich-text support. If a durable sample exists, expose `Відкрити останній локальний документ` as a secondary action before offering creation.
2. **Command boundary:** Every mutating control serializes an explicit typed command with a fresh command ID and displayed `baseRevision`, then awaits the core/WASM result. The browser UI MUST NOT edit document data, revision labels, history, audit entries, or hashes itself. It replaces displayed data only from a successful result DTO.
3. **Failure atomicity:** For a stale command, invalid anchor, duplicate command, or invariant failure, retain the current revision/hash/content summary and history exactly as before. Announce the stable machine-readable code plus Ukrainian explanation. Never silently retry, rebase, or target adjacent content.
4. **Undo/redo:** Successful undo/redo each create and display a new revision and audit event. Disable unavailable operations rather than hiding them. After success, return focus to the invoking control and announce the new revision.
5. **Save/reload/recover:** Disable only the operation currently in flight, retain other non-conflicting read-only inspection, and show an explicit in-progress text state. On save success use `Збережено локально — ревізія {revision}` only after durable completion. Recovery accepts only the core-verified result; a gap/hash mismatch is a visible failed recovery, never an inferred repaired document.
6. **Data minimization:** Render audit DTO fields only: IDs, revision links, timestamp, command category, source modality, outcome, safe error code, and redacted allowlisted metadata. Never render document text, command arguments, raw audio, raw transcripts, storage payloads, or hidden debug dumps in the UI or accessibility tree.
7. **No destructive UI:** Phase 1 exposes no delete, clear-storage, overwrite, export, or irreversible action. Therefore no confirmation dialog is specified. If a later implementation adds a local-data reset control, it is out of contract and requires a separate destructive-action specification.

| Token | Value | Usage |
|-------|-------|-------|

| 2xl | 48px | Major vertical break between header and main content |

## Typography

Use exactly these four sizes and two weights. Monospaced values may use `ui-monospace, SFMono-Regular, Menlo, Consolas, monospace` at the role’s declared size without adding a new typographic scale.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body / metadata | 16px | 400 | 1.5 |
| Label / button / table heading | 14px | 600 | 1.4 |
| Section heading | 20px | 600 | 1.2 |
| Page title | 28px | 600 | 1.2 |

Do not use all-caps, condensed copy, or a text size below 14px. Revision IDs and hashes may be truncated visually in a fixed-width container with a copy affordance, but their full value MUST be exposed through an accessible name or adjacent visually-hidden text.

|------|-------|-------|

| Destructive | `#B91C1C` | Future destructive actions only; do not use in Phase 1 controls |

Use `#334155` for primary text, `#475569` for secondary text, and `#CBD5E1` for borders. Use semantic status helpers only alongside text/icons: success `#166534`, warning `#B45309`, error/conflict `#B91C1C`. On white, all text and non-text control boundaries must meet WCAG AA contrast; never rely on color as the sole state signal.

Accent reserved for: `Створити тестовий документ`, durable-success state, keyboard focus, and the current inspector section. Secondary buttons are white with neutral borders; ordinary links and every interactive control are not automatically accent-filled.

## Accessibility and Localization

- Use native `<button>` and `<input>` controls; no clickable `div`/`span`. Controls have visible labels, keyboard focus, and disabled semantics through `disabled`, not only visual styling.
- Provide a 3px solid `#1D4ED8` focus ring with 2px offset. It is visible against both dominant and secondary surfaces and is never removed.
- Implement `Ctrl/Cmd+Z` and `Ctrl/Cmd+Shift+Z` only when an inspector control owns the command context; do not intercept browser shortcuts while a native text field is focused. Buttons retain the same operation and are the discoverable default.
- The status region is announced without moving focus. Errors and conflicts use `role="alert"`; success/pending messages use `aria-live="polite"`. Audit updates announce a concise count/outcome, not the entire table on every mutation.
- Set `lang="uk"` on Ukrainian content. All keys and parameterized messages support an English resource with no hard-coded word order around `{revision}` or `{code}`. Do not claim RTL support in this phase.
- Table headers use `<th scope>`; timestamps have a machine-readable `<time datetime>`. Full IDs/hashes are programmatically available, and copy buttons announce e.g. `Скопіювати повний хеш ревізії`.
- Respect `prefers-reduced-motion`; use no nonessential animation. Pending state is text plus a static progress indicator, not a spinner alone.

## Validation Expectations

The Phase 1 browser proof must exercise the visible inspector path in Chromium/Edge once the real browser test environment exists:

1. Create the sample and assert the visible revision, schema, hash, and redacted creation audit entry.
2. Apply the test mutation; assert that the UI updates only after a successful command result and a new revision appears.
3. Trigger the stale-command diagnostic; assert conflict copy/code appears and revision/hash/audit history have no unintended mutation entry.
4. Undo then redo; assert each creates a new displayed revision and audit entry.
5. Save, reload, and simulate recovery; assert the last durable revision is restored and save success is not announced before IndexedDB completion.
6. Inspect the accessibility tree: landmarks, button names, focus movement, status announcements, complete hash access, and absence of document text/raw audio/transcript in the audit region.
