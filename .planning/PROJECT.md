# FlowPDF

## What This Is

FlowPDF is a web-first document editor for Ukrainian- and English-language contracts, forms, reports, and similar professional documents. It combines a semantic rich-text flow format with a native PDF representation so users can edit text with document-wide reflow, add fillable fields, control editing by voice, and export interoperable PDF files without depending on a commercial PDF SDK.

The product owns its canonical document model, transaction system, layout and pagination engine, PDF writer, progressively expanded PDF reader/editor, and the conversion boundary between semantic flow documents and fixed-layout PDF pages.

## Core Value

A user can edit semantic document text naturally, with all following content repaginating correctly, and export the result as a visually consistent, selectable, form-capable PDF.

## Requirements

### Validated

- [x] Users can create, open, save, and version a canonical FlowDocument. — Validated in Phase 1.

### Active

- [ ] Users can edit Ukrainian and English rich text with correct selection, undo/redo, Unicode shaping, line breaking, and document-wide reflow.
- [ ] The layout engine paginates paragraphs, headings, lists, simple tables, images, headers, footers, and explicit page breaks deterministically.
- [ ] Incremental reflow produces the same result as a full layout while keeping active-page editing responsive.
- [ ] Users can add and configure semantic text, multiline, checkbox, radio, select, date, number, email, and signature fields.
- [ ] The system can export its display list through an owned deterministic PDF writer with embedded subset fonts, selectable Cyrillic text, links, annotations, and AcroForm widgets.
- [ ] A PDF generated by FlowPDF can restore the exact source FlowDocument through an associated source payload or server-side content-addressed source.
- [ ] The system can import a controlled subset of external PDFs into a visual scene and reconstruct a FlowDocument with provenance and confidence reporting.
- [ ] Unsupported imported PDF content remains visually preserved as an immutable opaque island instead of being silently corrupted.
- [ ] Users can make voice dictation and allowlisted editing commands through the same transactional command bus as keyboard and UI actions.
- [ ] Untrusted PDF, font, image, and audio inputs are processed with resource limits, isolation, validation, and deterministic failure behavior.

### Out of Scope

- Full Acrobat/PDFium/MuPDF compatibility in the first milestone — broad compatibility is a multi-year effort and must grow from a controlled subset.
- Exact semantic reconstruction of arbitrary third-party PDF files — PDF may not contain paragraph, table, or reading-order semantics.
- XFA, embedded PDF JavaScript, multimedia, 3D, geospatial PDF, and portfolios — high complexity with little value for the first product slice.
- Digital-signature creation, LTV, certification signatures, and preservation of signed-document editability — deferred until incremental revisions and validation are mature.
- Full PDF/A and PDF/UA certification — the semantic model must support future conformance, but certification is deferred.
- Complex floats, page footnotes, vertical writing, arbitrary multi-column flow, and unrestricted table fragmentation — deferred beyond the initial layout engine.
- Pixel-identical `external PDF -> Flow -> PDF` conversion — external import is explicitly best-effort and confidence-scored.
- Always-listening voice activation — push-to-talk and explicit command mode are the safe initial interaction.
- Real-time multi-user collaboration — transaction identities and stable anchors are designed for it, but CRDT/network collaboration is deferred.

## Context

- PDF is a fixed-layout object and graphics format. It cannot serve as the sole source of truth for document-wide rich-text reflow.
- FlowPDF therefore maintains separate semantic, layout-fragment, display-list, and physical PDF object models.
- Flow editing regenerates pagination and PDF output. Native PDF editing operates only on recognized local scene objects, annotations, fields, and page operations.
- FlowPDF-generated PDFs have a lossless source lane. External PDFs use semantic reconstruction, OCR when needed, and a fidelity-preserving hybrid lane.
- The original imported PDF remains immutable. Every edited/exported result is a new revision or derived document.
- Implementation is performed by one autonomous Codex executor. Work is decomposed into small, sequential, independently verified phases rather than assuming a parallel engineering team.

## Constraints

- **Execution**: A single autonomous implementer owns research, design, implementation, tests, verification, and review — phases must remain small and recoverable.
- **Core technology**: Rust owns the canonical model, transactions, layout, invalidation, PDF syntax, reading, and writing; the same core targets native execution and WebAssembly.
- **Web technology**: React and TypeScript provide the web shell; Web Workers isolate layout and PDF work from the UI thread.
- **Low-level primitives**: HarfBuzz, ICU/ICU4X, vetted font libraries, image codecs, compression libraries, and cryptographic libraries are reused rather than reimplemented.
- **Independence**: No commercial PDF SDK is required at runtime. External engines may be used only as development references and differential validators.
- **Languages**: Ukrainian and English are first-class in v1; the architecture must not block additional scripts or bidirectional text.
- **Compatibility**: Chrome and Edge are the initial supported browsers; Safari and Firefox follow after the editor core stabilizes.
- **Scale target**: The initial interactive target is ordinary documents up to 100–200 pages, with viewport-first layout and background pagination.
- **Determinism**: Layout depends on pinned font binaries, engine versions, fixed-point geometry, and versioned hyphenation data.
- **Security**: Imported PDFs are hostile input. Parsing, decompression, fonts, images, OCR, and embedded actions require strict limits and sandboxing.
- **Accessibility**: The visual canvas/display-list layer must be accompanied by an input host and synchronized semantic DOM; voice is an additional modality, never the only one.
- **Data integrity**: Unsupported content is surfaced explicitly and preserved; the system must not invent or silently discard semantic structure.

## Key Decisions

| Decision | Rationale | Outcome |
|----------|-----------|---------|
| FlowDocument is the canonical source of truth for reflow editing | PDF page operators do not reliably encode semantic document flow | ✓ Validated in Phase 1 |
| Maintain semantic AST, fragment tree, display list, and PDF object graph as separate models | Each model has different invariants and consumers | — Pending |
| Build the Flow engine and PDF writer before the general PDF reader | Controlled generation validates the core architecture without arbitrary-import complexity | — Pending |
| Implement the core in Rust with WASM and native targets | Shared deterministic behavior, portability, and memory safety for untrusted input | ✓ Validated in Phase 1 |
| Reuse HarfBuzz, ICU, font, codec, compression, and crypto primitives | Reimplementing standards-heavy primitives adds risk without product differentiation | — Pending |
| Treat external PDF import as reconstruction with confidence and provenance | Arbitrary PDF-to-semantic conversion is not lossless | — Pending |
| Embed or content-address the source FlowDocument for owned PDFs | Provides exact semantic round-trip for files generated by FlowPDF | — Pending |
| Keep original imported PDFs immutable | Edits, OCR, redaction, and regeneration can invalidate signatures and historical bytes | — Pending |
| Use semantic field anchors in Flow mode and page anchors in native PDF mode | Field widgets must follow reflow but remain fixed in native page editing | — Pending |
| Edit imported PDFs through a bounded Rust-owned object graph and fresh rewrite | Preserve supported reachable structures and refuse edits when content cannot be represented safely | Accepted in ADR-001; implementation pending |
| Treat redaction as destructive content removal with fail-closed validation | A visual cover or one structural check cannot establish secure removal | Accepted in ADR-001; implementation requires a human checkpoint and independent validators |
| Use one typed transactional command bus for UI, keyboard, API, and voice | Guarantees consistent authorization, undo, idempotency, and testing | ✓ Validated in Phase 1 |
| Start with a deliberately narrow PDF and layout subset | A universal engine cannot be delivered safely as the first increment by one implementer | — Pending |
| Keep semantic authority in Rust while TypeScript owns physical browser I/O and presentation | Prevents a second, divergent implementation of validation, mutation, recovery, and redaction | ✓ Validated in Phase 1 |
| Publish browser durability only after one atomic IndexedDB transaction completes and Rust revalidates recovery | Exact retries converge while partial, corrupt, stale, or divergent state fails closed | ✓ Validated in Phase 1 |
| Version canonical bytes, schema migrations, provenance, and privacy-minimized audit projections | Makes identity and recovery deterministic without silently inventing lineage or retaining document content in diagnostics | ✓ Validated in Phase 1 |
